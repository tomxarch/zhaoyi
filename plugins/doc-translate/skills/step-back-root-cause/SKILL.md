# 升维思考：别陷进打补丁的死循环

一个个修症状，修一处冒一处，就是陷进了死循环。这时要停下来，往上看一层：这些问题共同依赖的是哪个假设或设计？

## 1. 什么时候触发（出现任何一条就做，不用等用户问）
- 同一类问题出现第三次，或者换个输入又冒出变体。
- 修复越来越像补丁：特例判断、阈值、例外名单、“再加一道检查”。
- 指标在变差或原地打转：请求数、耗时、返工次数、用户不满意的次数。
- 用户反复表达同一种不满，或者对话在绕圈：我在给差不多的回答。

**不要用的时候**：问题只出现一次，或者明显是单点笔误。直接修，别过度升维。

## 2. 先停，再把症状摆在一起
不写下一个补丁。列一张表，每行一个最近的问题：

| 现象 | 发生在哪一步 | 当时怎么修的 | 修完后又出了什么 |

只看单个问题看不出规律，摆在一起才看得出。

## 3. 找共同依赖的假设
逐条问“这些问题是不是都经过同一处、都默认了同一件事”。常见的隐藏假设：
- **相信外部输出**：模型、接口、用户输入一定按格式、按顺序、一条对一条地回来。
- **默认前提**：输入一定是某种语言、编码、格式、大小；真实环境和测试时一样。
- **丢了结构或上下文**：把整体拆成碎片处理（表格拆成格子、文档拆成句子），碎片之间的关系没了。
- **缓存了没核对的结果**：错一次以后反复复用，修了代码也还在。
- **悄悄的降级路径**：失败后走的备用路径没被测过，反而出了新问题。

## 4. 验证这个根因，再动手
- 它能不能**同时解释表里所有问题**？只能解释一个的不是根因。
- 它能不能**预测一个还没见过的问题**？能预测的才可信。
- 主动找反例：有没有问题跟它对不上？

## 5. 设计结构性的修法
- **核对而不是相信**：结果对不上就整批作废重做，没核对过的结果不缓存、不写进输出。
- **核对要由自己来做，不要把核对的负担转给那个不可靠的部件。** 反面教训：让小模型多交回一份“原文开头”来核对，结果它连这个格式都交不好，失败和重试成倍增加，比原来还差。优先用不依赖对方配合的办法：选对方本来就容易做对的格式（比如直接拿原文当键），加上自己能算的检查（数字、长度、语言、重复）。
- **把关键前提变成明确的一步**：比如先统一判断原文语言，不要到处各自猜。
- **失败时保守降级**：宁可留原样并标出来，也不要把半成品或原始回复写进结果。
- 估一下代价：新做法会让请求、耗时、复杂度多出多少。

## 6. 先小范围试点，用真实条件验收
- 开工前写下**成功标准**和**放弃标准**，比如“串格降到 0，请求数不超过原来的 1.5 倍”。
- 用**暴露问题的那个真实案例**，在**最弱的真实环境**里测（免费小模型、慢网络、旧数据），不能只用模拟测试。模拟会按你的设想配合，真实环境不会。
- 新旧做法并排比，同时跑一遍回归，确认没把别的改坏。
- 达不到标准就回退，再看一层；不要在新做法上继续打补丁，那是又一个死循环。

## 7. 跟用户沟通
- 用大白话说根因：哪几个问题来自同一个假设，证据是什么。
- 给出改法、试点计划和代价；大改动先征得同意。
- 试点结果如实报告，包括没达标的部分。

## 反面清单
- 根因只能解释一个症状。
- 新做法依赖不可靠部件“多配合一点”。
- 只拿模拟测试就宣布成功。
- 一失败就推倒重来，或者在失败的新做法上继续堆补丁。
- 等用户来问“是不是有个核心问题”才开始想。

## 来源
